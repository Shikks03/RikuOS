## Rulings from the Plan A quality review of tasks 7–10 — 2026-09-07

The reviewer found nothing critical: the six shell files are byte-exact to the plan, the types match their callees, the failure path is total, the redirect is correctly placed and every class name resolves in both directions. Five findings deserved a ruling, and every one of them is in the plan's own code rather than in its execution.

- **R37 — the rail reads settings through a read-only accessor that never writes.** `getOsSettings()` is `updateOsSettings({})`: a `findOneAndUpdate` with upsert whose empty `$set` is kept non-empty only by the `updatedAt` timestamp Mongoose injects — so every page view in the `(app)` group was a primary write that stamped `OsSettings.updatedAt` with the page-view time. `osSettings.ts` gains `readOsSettings()`: `findOne({}).lean()`, returning the three setting values, and the schema defaults when no document exists yet — the same values the upsert would have created. The defaults live once, as `OS_SETTINGS_DEFAULTS` in the model file, used by both the schema and the fallback. The upsert accessor stays the only path that can *create* the singleton, which is what CLAUDE.md's one-accessor rule protects; CLAUDE.md's sentence is clarified to say so. `getOsSettings()` keeps its three cron/API callers. Not done: `{timestamps:false}` on the existing call — with an empty `$set` Mongoose then deletes `$set` and sends `{}`, a whole-document replacement; that fragility is now a sentence in `osSettings.ts`.
- **R38 — the rail's database read has a five-second deadline.** `connectDB` bounds server selection at 10 s and a stalled socket at 45 s, and nothing bounded the six `findOne`s; the rail is on every signed-in page, so a degraded Atlas held every response open for up to ~55 s. `src/lib/deadline.ts` exports `withDeadline(promise, ms, label)` — `Promise.race` against a timer that is always cleared — tested with fake timers in `src/lib/__tests__/deadline.test.ts`. `AgentsBlock` wraps connect + both reads in one `withDeadline` of `RAIL_READ_TIMEOUT_MS = 5000`; a timeout falls into the existing `catch` and renders the six em-dash badges, the same `unknown` any failure renders. Five seconds clears a cold Atlas connect with room and is half the server-selection bound. **Plan C's page read of the health snapshot is a Mongo read on the same path and takes the same helper** — a review checkpoint for Plan C.
- **R39 — the top bar's stamp is computed on the client at navigation time, and `TopBar.tsx` is a client component.** A layout is preserved across soft navigations: after one rail click the server-rendered stamp froze at the time the shell was first loaded, and on `/freelance` would have under-claimed the freshness of numbers that were in fact just read. (A `template.tsx` does not help: its server output is rendered with the parent segment and only its client tree remounts.) `TopBar` subscribes to `usePathname()` so it re-renders on every navigation and formats `new Date()` then, still `en-GB` / `Asia/Manila`; the first paint is the server's time, with `suppressHydrationWarning` on the one text node for the rare minute rollover. At minute precision the navigation time *is* the read time on both kinds of page: `/freelance` is rendered by the server at navigation, and queue/settings fetch their APIs on mount. `router.refresh()` re-renders it too. R25 stands — the stamp, nothing else, on every page. The plan's "NavList is the shell's only client island" was already loose (`LogoutButton` is one too); the shell has three, each for one reason. Spec §3.3 and the file map's "Server" for `TopBar.tsx` read with this.

## After the quality re-review of the fix pass — 2026-09-07

The fix pass (`22b9310`, `40a8cdc`) passed its spec review and its quality re-review; the reviewer confirmed each ruling's mechanism rather than its intent (R38's timer ordering and cleanup, R39's context propagation) and withdrew both of its earlier disagreements. Three small fixes and two refinements follow, in one commit, before Task 13 calls Plan A done. Task 11 is unblocked and does not wait for them.

- **R41 — a field the singleton does not carry reads as its schema default, never as `undefined`.** `.lean()` applies no defaults, so a singleton created before a toggle existed has no such key; `readOsSettings()` would have returned `monitoringEnabled: undefined`, `isSwitchedOff` reads `!undefined` as `true`, and four badges would have asserted `off` — the exact inference from absence the rail exists to refuse. Each of the three values is defaulted with `?? OS_SETTINGS_DEFAULTS.<field>` (`??`, so a stored `false` survives), and a fourth test feeds a document carrying only `chaserEnabled`. (The reviewer's aside that `getOsSettings()` shares the exposure is not quite right — Mongoose applies defaults when it hydrates a document, and only `.lean()` skips them — but the fix is right either way.)
- **R39 addendum — the stamp's dependency on the path is a `key`, not a subscription side effect.** The bare `usePathname()` call worked because a context change re-renders its consumers, but its value reached nothing, so a memoizing compiler (`reactCompiler` is one config line away) would be entitled to cache the tree and freeze the stamp again with nothing to catch it. `useMemo(…, [pathname])` was rejected: `pathname` unused inside the callback is an `exhaustive-deps` warning, and lint must not gain one. Instead `TopBar` renders `<Stamp key={pathname} />`, a child that formats `new Date()` in its own render: the key is the same on the server and at hydration (no remount), and a navigation changes it, remounting the child and recomputing the stamp. Machine-visible, lint-clean, compiler-proof.
- **Accepted from the reviewer:** the `OsSettings` model docblock drops "always queries with the empty filter `{}` and upserts" for CLAUDE.md's wording; `deadline.test.ts` pins that the timer fires *at* the bound (4999 ms still pending, then the last millisecond); the plan's four pre-fix code blocks (Task 8 `TopBar` and `LogoutButton`, Task 9 `AgentsBlock`, Task 10 `layout.tsx`) each gain a bold "Superseded" line pointing here, because the plan's verification model is byte-exactness and a re-run would quietly regress them; Task 13 step 5 gains a line to note how long the badges take to resolve on a cold load, and to raise `RAIL_READ_TIMEOUT_MS` if that is regularly above ~2.5 s. The double cast in `readOsSettings` stays — house style, and the copy-by-name plus its `toStrictEqual` test is the real guard. The JSX comment inside `.crumb` stays: it documents the single-text-node decision at the line it lives on.
- **Recorded, not changed:** on `/queue` an in-page refetch (a filter click, a decision) moves the data without moving the stamp, and after a rail click the stamp updates while the badges beside it are reused from the layout — each comment is individually accurate and the two can disagree by minutes. There is no automated test for R39 and none is practical without a component harness the repo does not have; Task 13 step 5 item 7 is the check.
